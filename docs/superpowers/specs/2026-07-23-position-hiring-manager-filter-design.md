# 岗位管理招聘负责人筛选设计

## 目标

在岗位管理列表中增加按招聘负责人筛选的能力，帮助用户快速查看指定负责人名下的岗位，同时保留查看全部岗位的默认行为。

## 已确认范围

- 招聘负责人筛选位于岗位状态筛选框左侧。
- 页面首次进入时不选择负责人，默认展示全部岗位。
- 用户可以清空已选择的负责人，恢复展示全部岗位。
- 不提供“未分配负责人”筛选项。
- 负责人筛选可以和岗位名称、岗位状态组合使用。
- 不改变岗位的查看、编辑、发布和删除权限。

## 前端设计

岗位列表页新增 `searchHiringManagerId` 状态，并在现有标题搜索框与岗位状态筛选框之间增加“招聘负责人”下拉框。

下拉框支持按负责人姓名或邮箱搜索，并允许清空。选项来自独立的岗位负责人接口，仅展示至少负责一个岗位的用户，避免列出与岗位筛选无关的账号。选择变化后，岗位列表请求携带 `hiring_manager_id`；未选择时不传该参数。

负责人选项与岗位列表分别加载。负责人选项加载失败时显示错误提示，但不阻止岗位列表展示或其他筛选功能使用。

## 后端设计

### 岗位列表筛选

`GET /positions` 新增可选查询参数：

- `hiring_manager_id: UUID | None`

路由将该参数传给岗位服务。服务在参数存在时增加 `Position.hiring_manager_id == hiring_manager_id` 的精确过滤，并继续叠加现有的标题和状态条件。参数缺省时保持当前返回全部岗位的行为。

### 负责人选项

新增受登录保护的 `GET /positions/hiring-managers` 接口。接口从岗位与用户关联数据中返回去重后的负责人，且只包含至少负责一个岗位的用户。每个选项包含：

- `id`
- `full_name`
- `email`

结果按姓名排序，供岗位列表筛选使用。该接口面向所有能够访问岗位管理页的已登录用户，避免复用仅管理员可访问的 `/auth/users`。

静态路由 `/hiring-managers` 必须定义在动态路由 `/{position_id}` 之前，避免被解释为岗位 UUID。

## 数据流

1. 页面加载岗位列表和负责人选项。
2. 默认不传 `hiring_manager_id`，返回全部岗位。
3. 用户选择负责人后，前端将负责人 ID 与当前标题、状态筛选条件一并提交。
4. 后端组合查询条件并返回匹配岗位及原有统计信息。
5. 用户清空负责人后，前端移除该参数并重新加载全部匹配岗位。

## 错误与边界处理

- 非法 UUID 由 FastAPI 参数校验返回 422，不执行模糊或字符串匹配。
- 选择一个当前没有匹配岗位的负责人时，列表正常显示为空。
- 删除或失效的负责人不会破坏已有岗位列表；负责人选项以实际岗位与用户的有效关联结果为准。
- 不新增数据库字段或迁移，复用现有 `positions.hiring_manager_id`。

## 测试与验收

后端自动化测试覆盖：

- 未传负责人时仍返回全部符合标题、状态条件的岗位。
- 传入负责人 ID 时只返回该负责人名下岗位。
- 负责人、状态和标题条件可以组合。
- 负责人选项去重，只返回实际负责岗位的用户。
- 未登录用户不能读取负责人选项。

前端执行 TypeScript 构建和 ESLint 检查。人工验收确认筛选框位置、默认全部、选择后结果、清空恢复以及与状态筛选组合使用均符合预期。

## 非目标

- 不默认筛选当前登录用户。
- 不提供“未分配负责人”筛选。
- 不调整招聘负责人的分配规则或岗位权限模型。
- 不增加分页、负责人多选或筛选条件持久化。
